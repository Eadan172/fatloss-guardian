# 减重守护台 · FatLoss Guardian

本地优先（Local-First）的个人减重与防反弹 Dashboard 工作台。**数据 100% 存储于本机浏览器 localStorage，零网络传输、零第三方 API**。支持 JSON 完整备份 / 导入恢复，跨设备无损迁移。

技术栈：Vite + React 18 + TailwindCSS · 图表为手写 SVG（无任何图表库依赖）· 无后端

---

## 一、开源选型对比结论

针对「防反弹监控 + 周期复盘 + 100% 本地化」三项硬需求，评估了两个最相关的 MIT 开源项目：

| 维度 | Townzc/liftcut-tracker（102★） | Cawlumm/lyftr（320★） |
|---|---|---|
| 技术栈 | Next.js + Supabase（Auth/Postgres/RLS） | Go + Gin + SQLite 后端，React + TS + Tailwind + Vite 前端 |
| 数据存储 | Supabase 云端 Postgres（guest 模式本地优先，但设计目标是迁移上云） | **单文件 SQLite，自托管，隐私模型优秀** |
| Docker | 有 Dockerfile（需 Supabase 环境） | `docker compose pull && up -d` 预构建镜像，体验最好 |
| 已有功能 | 训练计划、饮食记录、体重趋势、PDF 导出、AI 计划（DeepSeek/OpenAI/vLLM） | 800+ 动作库、训练计划、Gym 模式、营养、体重趋势图 |
| 防反弹安全区间/预警线 | ✘ 无 | ✘ 无 |
| 周/月周期复盘 | ✘ 无 | ✘ 无 |
| 100% 本地零网络 | ✘ 违反（Supabase 云依赖；AI 功能走网络，除非自建 vLLM） | ✔ 满足 |
| 改造成本评估 | **高**：需剥离 Supabase 换成本地存储、移除/本地化 AI 层、新增区间预警与复盘引擎，约等于重写数据层与一半 UI | **中**：SQLite 模型好但后端是 Go，新增「区间预警 + 复盘规则引擎」需改 Go 后端 + React 前端两侧，且要维护其构建链 |

**结论：两个项目都是优秀的「追踪器」，但都不具备防反弹安全区间、预警线与周期复盘能力。** liftcut-tracker 的 Supabase 云依赖直接违反「零网络」硬性要求；lyftr 隐私模型达标但双端改造（Go + React）成本高于自建轻量前端。减重工作台的核心差异化逻辑（预警判定、复盘规则、计划生成）全部集中在前端，因此**自建单页应用是总成本最低的路线**——本仓库即成果。

> 若你未来想要「多端同步 + SQLite 服务端」的完整方案，建议直接使用 lyftr 作为追踪底座，本项目可作为其防反弹模块的设计蓝本。

## 二、功能模块

1. **个性化计划生成（v2 引擎）**：建档时录入**运动水平 K1–K4、每周可训练天数、单次可投入时长、伤病限制、PAR-Q 安全筛查、期望周减重**；营养引擎按「每周体重百分比」设定安全缺口，并给出纤维 / 饮水 / 餐次拆分 / 一日参考餐单；训练引擎以「安全 → 水平 → 器械」三重闸门，从 **95 个分级动作**中编排与真实水平匹配的 7 天计划，并按 7 周周期化自动进阶。**详见下方「三、计划生成引擎 v2」。**
2. **防反弹监控**：安全体重区间 + 反弹预警线，判定依据为 **7 日体重均线**（过滤水分波动）；走势图含区间色带、预警虚线、越线红点，顶部横幅三级预警（正常/缓冲/警报）。建档时按「目标体重 ±2 kg、预警线 +1 kg」自动初始化。
3. **每日打卡**：体重、热量、三大营养素、饮水、睡眠、训练完成度与时长、压力自评（1–5）、备注；支持任意日期补记与修改。
4. **周期复盘**：近 7 天 / 近 30 天双视图，八项指标评分（打卡率、体重变化、热量、蛋白质、睡眠、压力、运动、饮水），输出「保持/关注/干预」三级建议，内置**防暴食心理干预、压力管理、睡眠修复**话术库。
5. **备份迁移**：一键导出完整 JSON；导入时做 schema 校验与版本迁移，支持跨设备无损恢复。
6. **本机文件自动备份**：任何模式（dev / preview / docker）下数据变化都自动防抖写入项目根目录 `data/backup.json`（docker 经 nginx WebDAV PUT 写入）；任何方式启动（任意端口、任意浏览器）时若本机浏览器无数据，自动从该文件恢复，**无需再手动导入**。
7. **运动课程库打卡联动**：Keep / 薄荷健康等 App 无开放接口，在「我的计划」页将跟练课程手动录入一次（名称 / 来源 / **上课日期** / 时长 / 课程链接；来源选「其他」可手填名称），打卡页按日期自动列出当日课程 —— 勾选即自动回填运动时长、全部完成自动标记训练，点课程名可跳转 App 课程页。
8. **两套锻炼方案可选**：「我的计划」与「每日打卡」均可切换**平台生成方案 / 运动软件跟课**。跟课模式直接列出课程库清单（今天的课程置顶高亮），当天无课时给出最近安排与录入引导，不再是一句空提示。
9. **专业动作链接**：计划与打卡中的专业动作名词（如「保加利亚分腿蹲」）自动链接到 fitwill.app 的动作介绍页；已逐条验证的动作走直达链接，其余回退到站内检索页，最长词优先匹配避免「深蹲」抢占「杠铃深蹲」。

## 三、计划生成引擎 v2（本次升级）

本节记录计划生成部分的改造：从「只看器械的固定模板」升级为「按真实运动水平分级编排的引擎」，代码位于 `src/lib/exerciseLibrary.js`、`src/lib/nutrition.js`、`src/lib/trainingEngine.js`，由 `src/lib/plan.js` 作为编排层合并输出。

### 3.1 改造前后对比

| 维度 | v1（改造前） | v2（本版） |
|---|---|---|
| 档案字段 | 性别 / 年龄 / 身高 / 体重 / 活动量 / 器械 / 饮食偏好 | 新增**运动水平 K1–K4**、每周可训练天数、单次可投入时长、伤病受限（多选）、PAR-Q 安全筛查、期望周减重 |
| 热量缺口 | 固定 TDEE × 15%，钳制 300–550 kcal | 以**每周体重百分比**为主约束（BMI ≥30 → 1.0%，≥28 → 0.8%，≥25 → 0.7%，正常 → 0.5%），再用 TDEE 百分比（25% / 30%）作上限兜底，摄入再锁 **1.1 × BMR** 地板 |
| 蛋白质 | 目标体重 × 1.6–2.0 g/kg（随饮食偏好） | 参考体重 × 1.7 g/kg，并受「总热量 40%」与「2.2 g/kg」**双上限**约束；肥胖者参考体重按目标体重或当前体重 75%–85% 计，避免按总体重推高目标 |
| 脂肪 / 碳水 | 脂肪 0.8 g/kg，碳水补差 | 脂肪**不低于 0.6 g/kg 且不低于总热量 20%**（激素与脂溶性维生素）；碳水 **80 g 保底**（大脑与力量训练供能） |
| 新增营养指标 | 无 | 膳食纤维（14 g/1000 kcal，下限男 30 / 女 25，上限 38）、饮水（33 ml/kg）、餐次与每餐蛋白质分配、一日参考餐单 |
| 动作来源 | 硬编码 3 套模板（无器械 / 哑铃 / 健身房），每套 7 天写死 | **95 个动作的分级动作库**，每个动作标注 `minLevel`（难度闸门）、`impact`（关节冲击）、`tags`（禁忌标签） |
| 难度匹配 | 无 —— 久坐零基础与训练一年以上的人拿到同一份计划 | **三重闸门过滤**：安全闸门（PAR-Q / 伤病 / 年龄 / 体重基数 → 推导允许的最大关节冲击）→ 水平闸门（K1 用户拿不到 K3 / K4 动作）→ 器械闸门（只用真正拥有的器械，健身房用户隐含拥有哑铃） |
| 训练分化 | 固定 7 天循环 | 按水平与频率自动选择：全身循环 / 上下肢分化 / 推拉腿分化；力量日**封顶**（K1 最多 3 天），多余天数转低强度有氧 |
| 进阶逻辑 | 无 | **7 周周期化**：适应期 → 建立期 → 加强期 → 减载周，按建档周数自动推进；初学者优先加「组数」而非追重量 |
| 强度表述 | 「4×力竭」等模糊写法 | **RIR（还剩几次余力）+ RPE（主观用力程度）**双表述；减脂期所有动作都不到力竭（力竭会显著延长恢复、抬高食欲） |
| 时长控制 | 无 | 按用户声明的单次时长做**预算校验**：先逐级降组数、再削减动作数，优先保住「蹲 / 推 / 拉 / 后链 / 核心」的身体部位覆盖 |
| 安全透明 | 无 | 输出**安全说明**与**已排除项**清单（如「所有高冲击（跳跃 / 冲刺类）动作（体重基数大）」），并解释每一条的排除原因 |

### 3.2 为什么必须改

旧版 `generatePlan(profile)` 内部是 `buildWorkout(profile.equipment)` —— 只接收「器械」一个参数，档案里根本没有运动水平字段。后果是**零基础用户和训练一年的用户拿到同一份计划**，而且是「俯卧撑 4×力竭」「波比跳」「深蹲跳」这类动作。对零基础 + 大体重的减脂人群，这是明确的受伤风险来源：跳跃类动作落地瞬间的冲击可达体重的 3–4 倍。

新版把「真实运动水平」作为一等公民，并且区分了两类风险 —— **落地冲击**（跳跃 / 冲刺，由冲击闸门管）与**脊柱负荷**（杠铃深蹲 / 硬拉，由水平闸门与腰椎禁忌管）。因此一个系统训练一年以上、BMI 29 的用户仍能拿到杠铃主项，不会被误伤。

### 3.3 数据迁移（自动、无损）

- schema **v2 → v3**。旧档案缺失的新字段一律按**最保守口径**补齐：`K1 + 每周 3 练 + 30 分钟 + 无伤病限制 + 无 PAR-Q 阳性`
- 旧计划通过 `plan.version !== 2` 识别，启动时**自动重建**（旧计划是用「只看器械」的逻辑生成的，对零基础用户难度过高）
- 打卡记录、运动课程库、防反弹安全区间设置**全部原样保留**，不受影响
- 旧版按「星期」安排课程的数据，自动迁移为该星期最近一次出现的具体日期

### 3.4 回归校验

```bash
npm run verify:plan
```

13 个场景的硬断言，覆盖七类不变量：

1. 无**水平越级**（用户拿不到高于自己等级的动作）
2. 无**器械越权**（不会出现用户没有的器械动作）
3. 无**禁忌冲突**（伤病标签命中的动作被排除而非降级）
4. **K1 全低冲击**（零基础一律不给跳跃 / 冲刺）
5. **单次时长预算**守住（不超出用户声明时长 + 弹性）
6. **营养地板**守住（热量下限、缺口上限、脂肪 0.6 g/kg、碳水 80 g）
7. **旧档案迁移**回落 K1，以及 **LinkedMove 动作链接集成**未被破坏

> `data/` 目录为本机自动备份数据（个人健康数据），已在 .gitignore 中排除，请勿提交。

## 五、一键启动

### 方式 A：本地开发

```bash
npm install
npm run dev
# 打开 http://localhost:5173
```

### 方式 B：生产构建预览

```bash
npm run build
npm run preview
```

### 方式 C：Docker 单容器

```bash
docker compose up -d --build
# 打开 http://localhost:8080
```

### 方式 D：双击一键启动（推荐 Windows 日常使用）

双击 `启动.bat` —— 自动拉起 Docker Desktop（如未运行）、构建启动容器、打开浏览器；双击 `停止.bat` 关闭。macOS / Linux 用 `./start.sh`。

> **数据不再与端口/域名绑定**：任何模式下数据变化都自动写入 `data/backup.json`；任何启动方式打开时若浏览器无数据，会自动从该文件恢复。浏览器数据与文件备份双保险，跨设备迁移仍可用「设置 → 导出 JSON」。
>
> **老用户一次性迁移**：若你的数据在此功能上线前已存在（存于某浏览器 localStorage），用**原来的浏览器+原来的地址**打开一次应用，数据即自动写入备份文件，此后任何方式启动均自动恢复。

### 方式 E：计划引擎回归校验（开发者）

```bash
npm run verify:plan
# 13 个场景硬断言：无水平越级 / 无器械越权 / 无禁忌冲突 / K1 全低冲击
# 单次时长预算 / 营养地板 / 旧档案迁移回落 / 动作链接集成
```

> 改动 `exerciseLibrary.js` / `trainingEngine.js` / `nutrition.js` / `plan.js` 后建议先跑一遍再提交。

## 六、隐私说明

- 运行时**没有任何网络请求**：无统计、无遥测、无 CDN、无外部字体（可自行抓包验证）。
- 数据仅存于本机浏览器；清除浏览器数据前请先导出备份。
- 本工具为自我管理经验工具，**不构成医疗或营养建议**；热量缺口、断食、疾病人群减重请咨询专业医师或注册营养师。
